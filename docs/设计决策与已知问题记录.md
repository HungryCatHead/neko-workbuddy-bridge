# 设计决策与已知问题记录

记录版本变化，以及实现过程中值得留档的技术决策与坑。踩坑统一写成「现象 → 原因 → 处理」，方便二次开发时对照。

> 这是开发向文档，不是使用文档。上手请看根目录的 [README](../README.md)。

## [0.1.0] — 2026-11-16

首个公开版本。

### 决策：纯文件队列，不做常驻服务

最初实现过一版 HTTP 回调方案：插件侧起一个本地 HTTP 服务，宿主把工具调用 POST 过来、同步等结果。放弃的三条理由：

1. **需要常驻进程**。宿主重启后外部工具注册丢失，任务静默失败，用户完全看不出来；
2. **重复注册**。与插件形态并存时，同一能力被挂两次，一次派活产生两条任务；
3. **对用户是额外负担**。端口占用、防火墙提示、卸载残留，都要人处理。

改为「文件夹即协议」：

```
queue/inbox/<task_id>.json      待办
queue/outbox/<task_id>.json     成果
queue/processed/tasks|results/  归档
queue/artifacts/                产出文件
```

双方都不知道对方是否在线，只靠文件状态推进。代价是响应从"实时"降到"分钟级"，用「处理完发现还有活，就自建一次 1 分钟后的续跑」补回来——平台的最小调度粒度是 1 小时，只靠轮询会很难用。

### 已知限制：响应延迟与唤醒机制（实测补充）

"纯文件队列"决定了双方不在线也能推进，代价是它不是实时的。下面三条是实测结论，二次开发前先读，避免走弯路。

**1. 平台调度最小粒度是 1 小时，分钟级轮询是假配置**

自动化调度只接受 `DAILY / HOURLY / WEEKLY / MONTHLY / YEARLY`，没有 `MINUTELY`。试过绕：

- `FREQ=HOURLY;INTERVAL=1;BYMINUTE=0,15,30,45` —— 平台**收下并原样保存**，但调度器忽略 `BYMINUTE`，`nextRunAt` 仍是从当前时刻 +1 小时。看着像成功，实际没生效。
- `BYHOUR` 只接受单个整数，不接受逗号多值。

判断方法：别看 `rrule` 存没存进去，要看 `nextRunAt` 是不是真落在预期的分钟点。

真正管用的是"命中续跑"：某一轮领到活后，自建 1 分钟后的 `once` 自动化接着跑，直到队列清空。所以延迟的实际分布是——**没有待办时平均等半小时、最长 1 小时**才被领走；一旦被领走，1 分钟一轮很快就清空。成果写回本身是秒级的，瓶颈只在"等被领走"这一段。

**2. 外部事件无法"戳醒"执行端**

执行端没有常驻进程，只有"用户发起一次对话"或"定时任务到点"时才运行。五条看似可行的唤醒路都堵着：

| 设想 | 结果 |
|---|---|
| 在插件内起后台定时器 | 宿主在生命周期函数返回后销毁事件循环，常驻任务从未运行（加心跳日志验证 0 条） |
| 调高定时自动化频率 | 见上一条，最小粒度 1 小时 |
| 派活方跨进程直接触发 | 自动化管理工具是执行端侧的，派活方（另一进程）调不到 |
| 借本机安装包 CLI 同步拉起 | CLI 是桌面端的内嵌组件，独立进程既拿不到当前会话鉴权、也没有自己的登录入口（登录在宿主图形界面里）；独立调用报"需要登录"却仍返回退出码 0 |
| 发邮件触发 | 见下一条，邮件不是触发器 |

结论：唯一可靠的即时触发是**用户主动发起一次对话**。想要"派活即秒回"，当前架构做不到，不值得在这上面反复折腾。

**3. 邮箱通道是收发工具，不是触发器**

智能体邮箱的能力是"给执行端一个地址，让它主动去收、读、发邮件"——工具全是主动拉取，**没有"收到新邮件 → 立即触发一次运行"的反向机制**。所以它解决的是"怎么把东西递进来"，不是"怎么叫醒执行端"。把"去看看队列"写进邮件正文，并不会让执行端醒来执行。

另外该邮箱需要使用者手动开通，未开通时工具返回 `not_bound`。单为队列桥接的触发场景，不必开通。

### 决策：队列放在插件自己目录里

曾把队列放在调用方的工作区目录，结果是清理工作区时连队列一起被删。现在默认 `<插件目录>/queue`，路径由 `__file__` 推导，插件搬到哪队列跟到哪。

覆盖优先级：

```
WORKBUDDY_BRIDGE_ROOT 环境变量  >  plugin.toml [bridge].root  >  <插件目录>/queue
```

### 决策：自启动只能走正式安装

宿主的设计约束：**开发态插件（直接加载未打包目录）一律手动启动**，不允许自启。想要开机自启必须打包成 `.neko-plugin` 再通过插件管理器导入，成为正式安装身份。

相关的两个细节：

- 界面上的「自动启动」开关写的是**运行时字段**，不是 `plugin.toml` 的 `auto_start`。改 toml 不会生效；
- `plugin.toml` 的 `entry` 必须写全模块路径 `plugin.plugins.workbuddy_bridge:WorkbuddyBridgePlugin`，少了 `plugin.plugins.` 前缀在开发态能加载、打包后报入口点为空。

### 决策：成果必须可验证

自测通过 ≠ 真机通过。宿主侧模型可能在没查成果的情况下回答"已完成"——这不是 bug，是能力边界。验收办法：在成果里埋一个随机标识，要求原样复述出来。第一次端到端验证就是靠这个才确认链路真通了。

### 约定：写成果用原子写

`outbox` 的成果先写 `.tmp` 再改名，避免读取端读到写了一半的 JSON。`inbox` 的任务一律只处理 `status == "pending"`，处理完移到 `processed/tasks/`，靠文件位置做幂等。

成果默认**读走即归档**：`check_workbuddy_results` 读一次后移到 `processed/results/`，同一份成果不会被念两遍。

### 已知坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 改了 `plugin.toml` 的 `root` 不生效 | 运行时配置目录下还有一份 `plugin.toml`，优先级高于源码里的默认值 | 两处都要改，改完重载插件 |
| 重装插件后任务丢失 | 重装覆盖插件目录 | 装前清空 `queue/inbox/` |
| 安装包里出现任务内容和成果文件 | 打包按插件目录整体收集，`queue/` 与 `.workbuddy/` 也在里面 | 打包前把这两个目录临时挪出，打完再挪回 |
| 覆盖安装后开机自启失效 | 自启动是运行时偏好，覆盖安装会重置 | 插件详情里重新打开「自动启动」 |
| 一次派活出现两个任务 | 同名插件的两份安装 | 插件管理器里删掉多余的一份 |
| `git count-objects` 与实际占用差异巨大 | NTFS 大簇（1 MB）下 `du` 统计失真 | 用 `git count-objects -vH` 看真实值 |
| Git Bash 下 `find` 找不到中文文件名 | 编码问题 + 相似目录名容易误判 | 改用 Python `os.walk` |
| 测试污染真实队列 | 测试直接写生产 `inbox` | 测试指向临时 root，跑完清理 |
| 自定义模型填本地代理地址报错 | 那不是 OpenAI 兼容端点 | 填真实 API 地址 |
| 自动化写了 `BYMINUTE` 却没按分钟跑 | 平台保存了字符串但调度器忽略，最小粒度仍是 1 小时 | 看 `nextRunAt` 验证，别只看 `rrule`；靠"命中续跑"补延迟 |
